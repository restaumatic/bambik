Code style

Comments are deliberately absent - code should read on its own. Imports are 100% explicit (including Prelude) - code is honest about its dependencies. Each demo is a complete application split into two listed modules with a one-way dependency: a view module entered at its single exported function, importing the design-system vocabulary and the logic module; and a logic module of pure business functions and data, depending only on the domain (no UI component types, no design system). The MDC2 | MDC3 twins are therefore two view modules sharing the exact same logic module - the design-system switch is a view-only diff. Each UI-related line leads with the visual concern with $ plumbing and trails with the data concern with # plumbing - no data word ever leads a line (an emitter's replay payload trails too: button @l { … } # with patch). A captioned leaf states its copy once, as its own type argument: nothing derives a caption from an identifier, so a label is the words it draws and is usually a quoted string, human copy being no identifier - filledTextField @"First name" {}, button @"Submit order" {} emitting [ "Submit order" :: _ ], quoted at every mention (atCase @"Submit order", match { "Submit order": … }); no demo passes an emitter label: at all: where a trace form's loop case would force two buttons to share one case under different words, the buttons are two business actions - each takes its own self-describing case and # toCases adopts it into the loop case (checkout's button @"Next" {} # toCases goneOn), leaving label: for a glyph-only face. An editor is held to the same rule, and no demo passes a caption config at all - the label carries the copy whole, punctuation and units included (filledTextField @"Start date (DD.MM.YYYY)" {}, sliderLive @"Amount (€)" {}); selector options follow the same rule through choice, one per case (dropdown @"Room" {} [ choice @"Focus pod (4 seats)", choice @"Boardroom (12 seats)" ]) - a plain array, so option order is the order written rather than the variant row's, which the compiler sorts alphabetically. And since a label is the copy, business code reads it back rather than restating it: a match whose branches merely echo their case labels - verbatim or re-cased - is deleted for caseText (Data.Variant.Case), the case label read verbatim, so options are labeled as the exact copy the line needs (choice @"with oat milk", choice @"cash"); a map that does real work (shortening, glyphs, per-case sentences) stays a named copy function. A case-invariant affix is not part of the copy: it factors out of the labels, stated once in the caption (@"Duration (min)" over choice @"15") or as line glue (caseText roast <> " roast"), while an affix that varies per case stays in the labels ("with whole milk"/"no milk"). Every line names exactly one semantic anchor - the model field it edits (@l on an editor, selector or labelled group - group @"Customer" $ … nesting a sub-record under a card surface, heading and accessible name in the same word, and leading its lines like any container), the business case it emits or shows (@l on an emitter, pane or status), the named read function it renders, or nothing at all, chrome writing nothing - so the view reads line by line into the model and the logic module: line ↔ named symbol, deliberately never line ↔ field. Copy is a function, not a field: a display whose content is copy takes the read function and no label - headlineSmall (text balanceLine) with balanceLine :: { balance :: Number } -> String in the logic module - so the view line names its own writer and the screen's copy is a pure function under unit test rather than a view-side bracket or a model field a display wanted. A whole line is one function, glue included - a prefix, a unit suffix, the words between two values - so staticText never shares a text run with a display leaf and survives only for wholly static copy; a bare field that is already copy is read with an accessor (text _.title), and inside a collection item or a pane the same function reads the row the producing projection built. A display that renders a number takes a read function too (progressBar @"Elapsed" elapsedFraction) - a fraction is derived, and derivation is the same act as formatting - keeping its label as the accessible name only, since a bar showing 42% must announce what is 42%; quantity editors are untouched, a slider genuinely editing its field. settled is left with its honest job, invariants among edited fields (temperature-converter's two scales, a room's seat bounds) - every surviving # settled in these demos sits on an editor, not one feeds a display. A business function takes at most one record of data - record parameters that travel together merge into one row whose labels name the roles (returnBetween { out, back }), fold handlers excepted: a handler takes updated's own Mealy shape, the payload then the retained state - match { refunded: applyRefund } over applyRefund :: { amount } -> { balance } -> { balance } - because an occurrence and a piece of knowledge are two records, not one row in disguise; scalar and Array payloads take the same shape positionally. An emitter that carries no payload of its own - a button fed the row it acts on, replaying it on click - is a state transformer rather than a Mealy step and takes the rung that says so: button @"Add" {} # applied addTodo over addTodo :: state -> state, the click's payload unread, so the label is stated once. A handler carries no field it does not touch: its row is exactly what it reads and writes, every field of a match's shared row is touched by some branch, and emitters with different patch rows group into separate stages. Business literals never hide in UI code: a slider edits a bounded quantity { current, min, max, step } whose bounds are model data flowing from the seed (never UI component config), and what legitimately stays config or seed content - tick periods, default payloads - is a named business definition (tickPeriod, gameStart - business language, never lifecycle words like initial or default), so UI code keeps only presentation. Application code never imports the ecosystem's Data.Profunctor (guardrail L16): projections ride their mechanisms - provided paneOf, foreach @l rowsOf, toCase @l payloadOf, forCase @"registered" welcomeLine - with identity saying verbatim; a shape with no mechanism is a missing-vocabulary signal for the library, never a raw lcmap/rmap. No nominal types in UI: view-model types are one-off and specific to this UI, so they earn no names - anonymous record and variant rows written in place, with no data, newtype, or type declarations in UI code. The code is compiled with a custom PureScript compiler with improved support for variants - anonymous sum types, dual to records: a variant type is written [ ok :: Int, err :: String ] the way a record is written { ok :: Int, err :: String }, and its cases are constructed with .ok 42.

Tracing

Every demo page runs with enabled tracing, so data propagation is logged to the browser console with [bambik] prefix. The spatial half of the same picture is the browser's own accessibility tree (DevTools → Elements → Accessibility): every component stamps its label — name on editors, the case label as a button's accessible name, role="group" + the heading on labelled groups — so the tree reads as the model itself (groups are sub-records, editors are fields with their current values), and a starving gate's warning logs the missing fields' elements, clickable in the console.
