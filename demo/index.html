Code style

Every demo follows these rules; the skill's writing.md states them in full, each once.

Modules

  • A view module and a view model module, one-way: the view exports one entry function and imports the design-system vocabulary and the view model; the view model holds pure business functions and values and imports only domain modules (Prelude, data modules, Effect, Aff, Data.Variant.Case); further modules are packaged controls (order-dashboard).
  • The view determines the view model: compiled with a typed hole for every imported value, it reports each at a type, and those types, their tails filled, are the view model's signatures (Record t0 -> String reported, countLine :: Count -> String written, never narrowed, never left open). Checked for every demo.
  • Twins share one view model: a design-system switch is a view-only diff.

Anchors

  • Every view line names exactly one anchor, in its own position: a model field as the type argument of an editor, selector or group (filledTextField @"First name", group @"Customer" $ …); a business case as the type argument of an emitter, pane or status (button @"Submit order", snackbar @"Card charged" captured); a copy function as a display's positional argument (text balanceLine); or nothing, for chrome (card, staticText "Hours").
  • A visible @"…" names a field or a case, nothing else; titles and static texts are strings (topAppBar "Espresso Bar"). A leaf's record holds only optional presentation ({ icon: "person_add" }, { columns: 80, rows: 3 }).
  • A stored field is named by its label, never picked with _.: textAt @"title", # providedAt @"halted" @"phase", listOfAt @"Message opened" @"id" @"messages".
  • The view writes no row: the model is the seed's signature (freshCount :: Count, type Count = { counted :: Int }), and a classifier's cases, a projection's element row, a payload and an action's outcomes are their functions' signatures (action @"Charge card" chargeFlaky, its outcomes closed by the statuses that tell them).

Labels and copy

  • A label is its caption verbatim and only the name — the words on the screen are the words in the code. A format, an example or a unit rides the primed sibling (filledTextField' @"Start date" { hint: "DD.MM.YYYY" }, sliderLive' @"Amount" { unit: "€" }), as does optional presentation (button' @"Place order" { icon: "local_cafe" }).
  • Options are leaves, one per case, in a VariantToVariant.do block in display order: option @"one-way flight", option @"return flight". A case label is read back with caseText, never restated in a match.
  • A display's text is a named copy function in the view model, the whole line including glue (balanceLine :: { balance :: Number } -> String); static copy is a literal in the view (staticText "Hours").
  • Events carry data, never copy. A status tells its case and the label is its whole copy, so an action names its outcomes as the words the user reads (Aff [ "Total missing" :: {}, "Order submitted" :: {} ]) and a status stands only after an action; a command straight from an emitter folds silently (fold @"Add" addTodo). What the user must keep is a model field shown by a display.

Types and values

  • No data or newtype in UI code; a shared row is a type synonym (type Trip = { … }). A row holds records, variants, String, Number, Int and Array.
  • No Maybe in the model (selected :: [ none :: {}, picked :: { index :: Int } ]); no Boolean unless a Boolean editor edits it (phase :: [ halted :: {}, timing :: {} ]).
  • Business values are model data (a slider edits { current, min, max, step } from the seed); constants have business names (tickPeriod, freshCount), never initial, default or seed.

Business functions

  • A handler updates the row it is given (increment m = m { counted = m.counted + 1 }); a constant replaces the model only whole, by reset @"New game" openingPosition.
  • Each event case has its own fold, applied to the model the event lands on: fold @"Count" increment; an event with a payload is foldInto @"Person picked" pick, its handler one record, pick :: { event :: Int, model :: Catalogue } -> Catalogue. Buttons and folds are one line of the view, ( … ) # stepped.
  • An action is opened by its progress indicator and stands after its button, followed by the statuses that tell its outcomes: one that returns the model is folded captured, one that changes nothing kept.

Wiring and layout

  • Never import the ecosystem's Data.Profunctor; a reshaping rides a word's argument (actedOf @l rowsOf). State lives in the model, and an application has one knot, # looped, around everything that changes it. Stock components only; custom style only for data-driven graphics.
  • No comments in a view; the view model says in -- | comments what each type and function means in the domain. Explicit imports, Prelude included.
  • A line leads with what is seen, via $ (headline4 $ text countLine, never parentheses), and trails with data words, via # (( headlineSmall $ text wonLine ) # inCase @"won" gameOutcome); a decorator trails its element. Two-space indentation; a closer or # chain never starts a line, except the knot's closer (# looped # with seed) and that of a broken row; a signature too long for its line takes one field per line.
  • Pipeline order: load, form, live summary, events, actions with their statuses, closed by the seed. The entry is body $ …; the page supplies the surface.

Compiler

  • A forked PureScript compiler adds variant sugar: a variant type is written [ ok :: Int, err :: String ] like a record type, and a case is built with .ok 42.

Tracing

Every demo page runs with tracing on: in the browser console, at the Verbose level, filter on [bambik] to see each value flow from stage to stage. DevTools → Elements → Accessibility shows the app as its model: every component is named by its label, so groups read as sub-records, editors as fields with their values and buttons as cases.
