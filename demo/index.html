Code style

Comments are deliberately absent - code should read on its own. Imports are 100% explicit (including Prelude) - code is honest about its dependencies. Each demo is a complete application split into two listed modules with a one-way dependency: a view module entered at its single exported function, importing the design-system vocabulary and the view model module; and a view model module of pure business functions and data, depending only on the domain (no UI component types, no design system), which the view determines: compiled with a typed hole for every value it imports, the view reports each at a concrete type with nothing unknown, so that hole list is the view model module's signatures. This holds because the model row is declared once, on the seed line (# mvu @( messages :: …, deletion :: … ) mondayMail), and every derived row where it is introduced - a classifier's cases on its first pane (# provided @"reading" @( reading :: …, browsing :: {} ) messageView), an action's outcome (# action @[ generated :: String ] samplePassword), a projection's element row, a payload, a trace form's state - while a stored field is read by a plain accessor (_.messages, # provided @"confirming" _.deletion); npm run check-determined verifies it for every demo. The MDC2 | MDC3 twins are therefore two view modules sharing the exact same view model module - the design-system switch is a view-only diff. Each UI-related line leads with the visual concern with $ plumbing and trails with the data concern with # plumbing - no data word ever leads a line (an emitter's replay payload trails too: button @l { … } # with payload), and a decorator rides its element rather than leading it (checkbox @"Loyalty" … # tooltipWith loyaltyNote, never tooltip … $ checkbox …, which would put chrome where the anchor belongs). A captioned leaf states its copy once, as its own type argument: nothing derives a caption from an identifier, so a label is the words it draws and is usually a quoted string, human copy being no identifier - filledTextField @"First name" {}, button @"Submit order" {} emitting [ "Submit order" :: _ ], quoted at every mention (atCase @"Submit order", match { "Submit order": … }); no demo passes an emitter label: at all: where a trace form's loop case would force two buttons to share one case under different words, the buttons are two business actions - each emits its own self-describing case and # toCase introduces the loop case from it (checkout's button @"Next" {} # toCase @"next" goneOn), leaving label: for a glyph-only face. An editor is held to the same rule, and no demo passes a caption config at all - the label carries the copy whole, punctuation and units included (filledTextField @"Start date (DD.MM.YYYY)" {}, sliderLive @"Amount (€)" {}); selector options follow the same rule through choice, one per case (dropdown @"Room" {} (choice @"Focus pod (4 seats)" <+> choice @"Boardroom (12 seats)")) - one-option arrays joined by <+>, so option order is the order written rather than the variant row's, which the compiler sorts alphabetically, and the row the field holds is closed by the list. And since a label is the copy, business code reads it back rather than restating it: a match whose branches merely echo their case labels - verbatim or re-cased - is deleted for caseText (Data.Variant.Case), the case label read verbatim, so options are labeled as the exact copy the line needs (choice @"with oat milk", choice @"cash"); a map that does real work (shortening, glyphs, per-case sentences) stays a named copy function. A case-invariant affix is not part of the copy: it factors out of the labels, stated once in the caption (@"Duration (min)" over choice @"15") or as line glue (caseText roast <> " roast"), while an affix that varies per case stays in the labels ("with whole milk"/"no milk"). Every line names exactly one semantic anchor - the model field it edits (@l on an editor, selector or labelled group - group @"Customer" $ … nesting a sub-record under a card surface, heading and accessible name in the same word, and leading its lines like any container), the business case it emits or shows (@l on an emitter, pane or status), the named read function it renders, or nothing at all, chrome writing nothing - so the view reads line by line into the model and the view model module: line ↔ named symbol, deliberately never line ↔ field. Each anchor sits in its own position - a field or case as the leaf's type argument, a read function as its positional argument - so every leaf reads as a noun phrase: its word, its anchor, then its positional arguments (snackbar @"booked" bookedLine, topAppBar @"Espresso Bar") - and a record holds only optional presentation (button @"Sign up" { icon: "person_add" }), never what the line is about. Wrappers are minimal: editors that share a card share a model sub-record - group @"Customer" $ … - a blind card holds only content that edits nothing (a summary, a preview), and the app takes no surface of its own: the entry reads body $ …, the page it is shown on framing it. Indentation is two spaces per nesting step, closers back at their opener's column. Copy is a function, not a field: a display whose content is copy takes the read function and no label - headlineSmall (text balanceLine) with balanceLine :: forall r. { balance :: Number | r } -> String in the view model module - so the view line names its own writer and the screen's copy is a pure function under unit test rather than a view-side bracket or a model field a display wanted. A whole line is one function, glue included - a prefix, a unit suffix, the words between two values - so staticText never shares a text run with a display leaf. Fixed copy is static or constant: a static is on screen before and regardless of any data (a heading, a note, a caption) and is written as a type, staticText @"Hours"; a constant shows only through data (a sentence's glue, a pane's message) and lives in a copy function (text faultLine # shownWhen @"faulty" readout); a bare field that is already copy is read with an accessor (text _.title), and inside a collection item or a pane the same function reads the row the producing projection built. A display that renders a number takes a read function too (progressBar @"Elapsed" elapsedFraction) - a fraction is derived, and derivation is the same act as formatting - keeping its label as the accessible name only, since a bar showing 42% must announce what is 42%; quantity editors are untouched, a slider genuinely editing its field. settled is left with its honest job, invariants among edited fields (temperature-converter's two scales, a room's seat bounds) - every surviving # settled in these demos sits on an editor, not one feeds a display. A business function takes at most one record of data - record parameters that travel together merge into one row whose labels name the roles (returnBetween { out, back }), fold handlers excepted: a handler takes updated's own Mealy shape, the payload then the retained state - match { refunded: applyRefund } over applyRefund :: { amount :: Number | r1 } -> { balance :: Number | r2 } -> { balance :: Number | r2 } - because an occurrence and a piece of knowledge are two records, not one row in disguise; scalar and Array payloads take the same shape positionally. An emitter that carries no payload of its own - a button fed the row it acts on, replaying it on click - is a state transformer rather than a Mealy step and takes the rung that says so: button @"Add" {} # applied addTodo over addTodo :: state -> state, the click's payload unread, so the label is stated once. A handler carries no field it does not touch: its row is exactly what it reads and writes, every field of a match's shared row is touched by some branch, and emitters with different footprints group into separate stages. Every business function states its footprint as an open row - countLine :: forall r. { count :: Int | r } -> String - exactly the fields it names, checked by unification against the row the stage is fed, which is what lets each view run while its view model is still holes (every view model export a bare hole, the initial UI still on screen); a function returning the row it was given updates it (increment m = m { count = m.count + 1 }), so a preset is such an update (button @"Reset" {} # applied restarted), never a constant patch; a constant replaces the model only whole (button @"New game" { icon: "replay" } # with openingPosition # updated (match { "New game": const })). An action's outcome cases are named where the action is: a single-outcome action's case on its own line (action createPerson # atCase @"Create" # toCase @"created" identity), a multi-outcome action's cases consumed by its statuses right after it. Business literals never hide in UI code: a slider edits a bounded quantity { current, min, max, step } whose bounds are model data flowing from the seed (never UI component config), and what legitimately stays config or seed content - tick periods, default payloads - is a named business definition (tickPeriod, gameStart - business language, never lifecycle words like initial or default), so UI code keeps only presentation. Application code never imports the ecosystem's Data.Profunctor (guardrail L16): projections ride their mechanisms - provided paneOf, foreach @l rowsOf, toCase @l payloadOf, snackbar @"registered" welcomeLine - with identity saying verbatim; a shape with no mechanism is a missing-vocabulary signal for the library, never a raw lcmap/rmap. No nominal types in UI: view-model types are one-off and specific to this UI, so they earn no names - anonymous record and variant rows written in place, with no data, newtype, or type declarations in UI code. The code is compiled with a custom PureScript compiler with improved support for variants - anonymous sum types, dual to records: a variant type is written [ ok :: Int, err :: String ] the way a record is written { ok :: Int, err :: String }, and its cases are constructed with .ok 42.

Tracing

Every demo page runs with enabled tracing, so data propagation is logged to the browser console with [bambik] prefix. The spatial half of the same picture is the browser's own accessibility tree (DevTools → Elements → Accessibility): every component stamps its label — name on editors, the case label as a button's accessible name, role="group" + the heading on labelled groups — so the tree reads as the model itself (groups are sub-records, editors are fields with their current values), and a starving gate's warning logs the missing fields' elements, clickable in the console.
