Code style

Comments are deliberately absent - code should read on its own. Imports are 100% explicit (including Prelude) - code is honest about its dependencies. Each demo is a complete application split into two listed modules with a one-way dependency: a view module entered at its single exported function, importing the design-system vocabulary and the logic module; and a logic module of pure business functions and data, depending only on the domain (no UI component types, no design system). The MDC2 | MDC3 twins are therefore two view modules sharing the exact same logic module - the design-system switch is a view-only diff. Each UI-related line leads with the visual concern with $ plumbing and trails with the data concern with # plumbing - no data word ever leads a line (an emitter's replay payload trails too: button @l { … } # with patch). A captioned leaf states its copy once, as its own type argument: nothing derives a caption from an identifier, so a label is the words it draws and is usually a quoted string, human copy being no identifier - filledTextField @"First name" {}, button @"Submit order" {} emitting [ "Submit order" :: _ ], quoted at every mention (atCase @"Submit order", match { "Submit order": … }); no demo passes an emitter label: at all: where a trace form's loop case would force two buttons to share one case under different words, the buttons are two business actions - each takes its own self-describing case and # toCases adopts it into the loop case (checkout's button @"Next" {} # toCases goneOn), leaving label: for a glyph-only face. An editor is held to the same rule, and no demo passes a caption config at all - the label carries the copy whole, punctuation and units included (filledTextField @"Start date (DD.MM.YYYY)" {}, sliderLive @"Amount (€)" {}); selector options follow the same rule through choice, one per case (dropdown @"Room" {} [ choice @"Focus pod (4 seats)", choice @"Boardroom (12 seats)" ]) - a plain array, so option order is the order written rather than the variant row's, which the compiler sorts alphabetically. And since a label is the copy, business code reads it back rather than restating it: a match whose branches merely echo their case labels - verbatim or re-cased - is deleted for caseText (Data.Variant.Case), the case label read verbatim, so options are labeled as the exact copy the line needs (choice @"with oat milk", choice @"cash"); a map that does real work (shortening, glyphs, per-case sentences) stays a named copy function. A case-invariant affix is not part of the copy: it factors out of the labels, stated once in the caption (@"Duration (min)" over choice @"15") or as line glue (caseText roast <> " roast"), while an affix that varies per case stays in the labels ("with whole milk"/"no milk"). Displays are verbatim (the presentation-model rule): everything the user reads is a model field - a formatted readout, a unit-suffixed quantity, a sentence composed from several fields - written by one normalization present<App> in the logic module, run as # settled present<App> trailing the pipeline with the seed pre-normalized, so the screen's copy is a pure function under unit test rather than a view-side bracket; the view keeps only case-invariant chrome (staticText "Till balance: €" beside text @"balanceText"), and a collection item's text fields are written by the projection that produces its rows. A business function takes at most one record of data - record parameters that travel together merge into one row whose labels name the roles (returnBetween { out, back }), fold handlers excepted: a handler takes updated's own Mealy shape, the payload then the retained state - match { refunded: applyRefund } over applyRefund :: { amount } -> { balance } -> { balance } - because an occurrence and a piece of knowledge are two records, not one row in disguise; scalar and Array payloads take the same shape positionally. An emitter that carries no payload of its own - a button fed the row it acts on, replaying it on click - is a state transformer rather than a Mealy step and takes the rung that says so: button @"Add" {} # applied addTodo over addTodo :: state -> state, the click's payload unread, so the label is stated once. A handler carries no field it does not touch: its row is exactly what it reads and writes, every field of a match's shared row is touched by some branch, and emitters with different patch rows group into separate stages. Business literals never hide in UI code: a slider edits a bounded quantity { current, min, max, step } whose bounds are model data flowing from the seed (never UI component config), and what legitimately stays config or seed content - tick periods, default payloads - is a named business definition (tickPeriod, gameStart - business language, never lifecycle words like initial or default), so UI code keeps only presentation. Application code never imports the ecosystem's Data.Profunctor (guardrail L16): projections ride their mechanisms - provided paneOf, foreach @l rowsOf, toCase @l payloadOf, forCase @"registered" welcomeLine - with identity saying verbatim; a shape with no mechanism is a missing-vocabulary signal for the library, never a raw lcmap/rmap. No nominal types in UI: view-model types are one-off and specific to this UI, so they earn no names - anonymous record and variant rows written in place, with no data, newtype, or type declarations in UI code. The code is compiled with a custom PureScript compiler with improved support for variants - anonymous sum types, dual to records: a variant type is written [ ok :: Int, err :: String ] the way a record is written { ok :: Int, err :: String }, and its cases are constructed with .ok 42.

Tracing

Every demo page runs with enabled tracing, so data propagation is logged to the browser console with [bambik] prefix.
