Code style

Comments are deliberately absent - code should read on its own. Imports are 100% explicit (including Prelude) - code is honest about its dependencies. Each demo is a complete application split into two listed modules with a one-way dependency: a view module entered at its single exported function, importing the design-system vocabulary and the logic module; and a logic module of pure business functions and data, depending only on the domain (no widget types, no design system). The MDC2 | MDC3 twins are therefore two view modules sharing the exact same logic module - the design-system switch is a view-only diff. Each UI-related line leads with the visual concern with $ plumbing and trails with the data concern with # plumbing - no data word ever leads a line (an announced button payload trails too: button { … } # with patch # asCase @l). Simple text concatenation is UI structure (guardrail A11): a displayed line glued from fields and literal separators is a merge of staticText pieces and per-field text displays, each field updating its own text node in place - business functions format values (euros, formatTime), never assemble lines; toast copy (a String channel) and shape-varying lines are the exemptions. A business function takes at most one record of data (guardrail A12) - record parameters that travel together merge into one row whose labels name the roles (returnBetween { out, back }), fold handlers included: informed lays the event's fields over the retained model's (fresh knowledge wins), so a handler reads one row of facts - match { refunded: informed applyRefund } over applyRefund :: { amount, balance } -> { balance }; only scalar and Array payloads stay positional. A handler carries no field it does not touch (guardrail A13): its row is exactly what it reads and writes, every field of a match's shared row is touched by some branch, and emitters with different patch rows group into separate stages. Business literals never hide in UI code: a slider edits a bounded quantity { current, min, max, step } whose bounds are model data flowing from the seed (never widget config), and what legitimately stays config or seed content - tick periods, default payloads - is a named business definition (tickPeriod, gameStart - business language, never lifecycle words like initial or default), so UI code keeps only presentation. Application code never imports the ecosystem's Data.Profunctor (guardrail A9): projections ride their mechanisms - provided paneOf, foreach @l rowsOf, toCase @l payloadOf, forCase @l copyOf - with identity saying verbatim; a shape with no mechanism is a missing-vocabulary signal for the library, never a raw lcmap/rmap. No nominal types in UI: view-model types are one-off and specific to this UI, so they earn no names - anonymous record and variant rows written in place, with no data, newtype, or type declarations in UI code. The code is compiled with a custom PureScript compiler with improved support for variants - anonymous sum types, dual to records: a variant type is written [ ok :: Int, err :: String ] the way a record is written { ok :: Int, err :: String }, and its cases are constructed with .ok 42.

Tracing

Every demo page runs with enabled tracing, so data propagation is logged to the browser console with [bambik] prefix.
