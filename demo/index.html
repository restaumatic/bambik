Code style

Every demo follows one contract for application code, stated in full in the skill's writing.md. In short:

Two modules

  • A view and a view model. The view module exports one entry function and imports the design-system vocabulary and the view model module. The view model module holds pure business functions and data and depends only on the domain. A demo that fakes a backend (crud) or packages its own controls (order-dashboard) lists that module too.
  • The view determines the view model. Compiled with a typed hole for every value it imports, the view reports each one at a concrete type, and that list is the view model module's signatures, verbatim. npm run check-determined verifies it for every demo.
  • Twins share the view model. A demo's MDC2 and MDC3 versions are two views over one view model module, so switching design system is a view-only diff.

Every line names one anchor

  • One anchor per line: the model field it edits (filledTextField @"First name" {}, group @"Customer" $ …), the business case it emits or shows (button @"Submit order" {}, snackbar @"booked" bookedLine), the copy function it renders (text balanceLine), or nothing, for chrome. A visible @"…" always names a row label: a field or a case.
  • A leaf reads as a noun phrase: word, anchor, then positional arguments. A record holds only optional presentation (button @"Sign up" { icon: "person_add" }), never what the line is about.
  • A label is the copy it draws, punctuation and units included (sliderLive @"Amount (€)" {}), so no demo passes a caption config. Business code reads a case label back with caseText instead of restating it.
  • Selector options are one choice per case, joined by <+> in the order written (choice @"Focus pod (4 seats)" <+> choice @"Boardroom (12 seats)").

Layout

  • No comments, explicit imports. Code reads on its own, and every import names what it uses, Prelude included.
  • What is seen leads, data trails. A line leads with its element via $ and trails with data concerns via #. A decorator rides its element (checkbox @"Loyalty" … # tooltipWith loyaltyNote) and never leads the line.
  • Two-space indentation, closers back at their opener's column. The app takes no surface of its own: the entry reads body $ …, and the page frames it.
  • The architecture reads off the pipeline: load, form, live summary, events, each action with its statuses, closed by the seed.

Types and values

  • The model is declared once, where it first appears: on the seed line (# looped @( counted :: Int ) # with freshCount) or by a load action's outcome. A derived row is declared where it is introduced, such as a classifier's cases on its first pane, and a stored field is read with a plain accessor (_.messages).
  • No nominal types in UI. No data, newtype or type declaration for anything a component shows or emits. Rows hold records, variants, primitives and arrays. There is no Maybe, and no Boolean unless a Boolean editor edits it.
  • Copy is a function, not a field. A display's text comes from a named copy function in the view model module, glue included: headlineSmall (text balanceLine) with balanceLine :: { balance :: Number } -> String. The screen's copy is then unit-testable. Fixed copy that needs no data is a static value, staticText "Hours".
  • Business values are model data, never UI literals. A slider edits a bounded quantity { current, min, max, step } whose bounds come from the seed, and what stays constant, like a tick period, is a named business value.

Business functions

  • The signature is the hint, verbatim: the row the stage is fed, closed (countLine :: { counted :: Int } -> String). It is never narrowed to the fields the body reads and never opened with a tail.
  • Update the row you are given (increment m = m { counted = m.counted + 1 }). A constant replaces the model only whole, in a fold.
  • Every event has a fold of its own, opened by its status as an action is opened by its progress indicator: snackbar @"Count" countedLine # fold increment. A fold nothing needs telling about opens with blankStatus. An event with a payload of its own is # joined with the model and handled by one function of one record, { event, model }.
  • One record per business function. Records that travel together merge into one row whose labels name the roles (returnBetween { out, back }).

Wiring

  • Speak the vocabulary. Application code never imports the ecosystem's Data.Profunctor. Every reshaping rides a word's own argument (foreach @l rowsOf, toCase @l payloadOf), with identity meaning "the value as it is".
  • State lives in the model. No FFI stashes, window globals or hidden loop channels. A stand-in server is a module of its own (crud).
  • Lean on the design system. No custom layout; custom style is for data-driven graphics only, such as an SVG canvas or a colour swatch.

The code is compiled with a custom PureScript compiler with improved support for variants - anonymous sum types, dual to records: a variant type is written [ ok :: Int, err :: String ] the way a record is written { ok :: Int, err :: String }, and its cases are constructed with .ok 42.

Tracing

Every demo page runs with enabled tracing, so data propagation is logged to the browser console with [bambik] prefix. The spatial half of the same picture is the browser's own accessibility tree (DevTools → Elements → Accessibility): every component stamps its label — name on editors, the case label as a button's accessible name, role="group" + the heading on labelled groups — so the tree reads as the model itself (groups are sub-records, editors are fields with their current values), and a starving gate's warning logs the missing fields' elements, clickable in the console.
