How a bambik app is written

Every demo page on this site shows a finished listing. This page shows what a listing hides: the session that produces one — the order the code is written in, and what the compiler says back after each step. The session below is real: the app is the counter demo in the two-module layout every bambik app ships with (a view module and a logic module beside it), and every compiler response is verbatim output of bambik's pinned PureScript compiler (0.15.16, the variant fork), captured by replaying the session.

The method rests on one rule, the anchor invariant (see the code style note): every view line names exactly one semantic anchor — the model field it edits (@l on an editor or selector), the business case it emits or shows (@l on an emitter, pane or status), the named read function it renders, or nothing at all, chrome writing nothing. So the view is written first, with typed holes (?countLine — a name the compiler must type rather than resolve) standing in for the functions that do not exist yet, and the logic module is written second, to the names and types the view demanded.

1 · The view, whole, before any logic exists

You know what the screen is before you know what the model is: a headline showing a count, a button that increments it. Write exactly that. Three term obligations enter as holes — the display's read function, the button's handler, the seed. Note what is not a hole: the field and case anchors (@"Count") and the chrome (elevation5, card, headlineLarge) are complete as written.

src/Counter.purs

module Counter (counter) where

import Prelude ((#), ($), Unit)

import Effect (Effect)
import PUI (applied, mvu)
import PUI.Web.HTML (body, shown, text)
import PUI.Web.MDC3 (button, card, elevation5, headlineLarge)
import QualifiedDo.Category as Category

counter :: Effect Unit
counter =
  body $
    elevation5 $
      card $ ( Category.do
          headlineLarge (text ?countLine) # shown
          button @"Count" {} # applied ?increment
      ) # mvu ?freshCount

The first decision of the session: this line shows a count. Write the read function down, its footprint stated as a closed row.

4 · Green

Every anchor resolved: countLine and increment are pure functions under unit test in the logic module, @"Count" is both the button's caption and its event case, and the chrome names nothing because it writes nothing. This is the app running as the counter demo — same two modules, the view in MDC3's vocabulary.

5 · Compile-green is not done

The types prove the wiring, not that data reaches the screen: a record merge withholds until every field of its row has been fed, so the session ends by running the app. A pane that stays blank is a knowledge gate withholding — and it is a named failure, not a mystery: the 3-second starvation watchdog prints the gate and its missing fields to the console, and the emission trace logs every propagation decision (see the tracing note). Here the seed feeds the one gate, the headline renders 0, and the session is over.

Aside · where the compiler speaks first

The session above had to decide every footprint itself, because its holes sat at subsuming positions — stages that deliberately read a sub-row of their pipeline's row. At pinned positions the roles reverse and the hole reports its full type, suggestions included. A status line over a payload the pipeline already fixed:

  body $
