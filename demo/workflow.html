How a bambik app is written

Every demo page on this site shows a finished listing. This page shows what a listing hides: the session that produces one — the order the code is written in, and what the compiler says back after each step. The session below is real: the app is a small pizza-order form — a text field, a live line, an Order button that places the order, a snackbar telling the outcome — in the two-module layout every bambik app ships with (a view module and, beside it, the view model module the view determines), and every compiler response is verbatim output of bambik's pinned PureScript compiler (0.15.16-variant.9, the variant fork), captured by replaying the session. The screenshots at the end are the session's own app, running.

The method rests on one rule, the anchor invariant (see the code style note): every view line names exactly one semantic anchor — the model field it edits (@l on an editor or selector), the business case it emits or shows (@l on an emitter, pane or status), the named read function it renders, or nothing at all, chrome writing nothing. So the view is written first, with typed holes (?orderLine — a name the compiler must type rather than resolve) standing in for the functions and actions that do not exist yet, and the view model module is written second, to the names and types the view demanded: the compiler's last message lists every hole with its type, and that list is the module's signatures, with nothing unknown. The model row is declared once, on the seed line, and a row no model field holds — a classifier's cases, an action's outcome — where it is introduced (see the code style note); that is what keeps the list concrete.

1 · The view, whole, before any logic exists

You know what the screen is before you know what the model is: a field for the pizza, a line showing what's in the oven, a button that places the order, a toast that tells the outcome. Write exactly that. Three term obligations enter as holes — the display's read, the action, the seed. Note what is not a hole: the field anchor (@"Pizza"), the case anchors (@"Order", stated once on the button and once on the action that takes its case; @"Pizza ordered", the outcome the snackbar tells — a status shows its case label and nothing else, so the outcome's name is the words on the screen), the model row on the seed line (@( "Pizza" :: String )) and the chrome (headlineSmall) are complete as written.

src/MDC3.purs

module Order.MDC3 (order) where

import Prelude ((#), ($), identity, Unit)

import Effect (Effect)
import PUI (action, atCase, looped, with)
import PUI.Web (text)
import PUI.Web.MDC3 (body, button, filledTextField, headlineSmall, indeterminateLinearProgress, snackbar)
import QualifiedDo.Semigroupoid as Semigroupoid

order :: Effect Unit
order =
  body $ Semigroupoid.do
    filledTextField @"Pizza"
    headlineSmall $ text ?orderLine
    button @"Order"
    indeterminateLinearProgress # action ?placeOrder # atCase @"Order"
    snackbar @"Pizza ordered" identity
  # looped @( "Pizza" :: String ) # with ?start

The compiler answers with a message per hole and a last one listing them together, and none of them is a refusal: every hole comes back typed. The display read reports { "Pizza" :: String } -> String, the seed exactly that row — the editor's field anchor and the model row declared on the seed line fixed the model before any logic exists — and the action reports its whole contract, { "Pizza" :: String } -> Aff [ "Pizza ordered" :: { "Pizza" :: String } ]: the snackbar folds its outcome with identity back into the loop, so the outcome must be the model, and the status's case names it:

Two things to read here. First, the last message is the one to read when there are many holes: it lists every hole with its type, and nothing in it is unknown — the model row on the seed line and the fold that closes the loop saw to that. And holes need not stop you from seeing the view: import hole from PUI.Web and substitute it for every hole, and the view compiles and runs — the field, the button and an empty line on screen, no data flowing, before a single business function exists (guardrails L18). Second, the reported type is the signature: the row the seed line declared is what the function is given, so write the hint down as it stands. Which of the row's fields the body reads is the body's business, not the signature's. This line shows the pizza.

5 · A slip, and where the compiler points

Now make the most common first slip: write the heading after the button, so the code order no longer matches the screen. Code order is data order, so the display is now fed what the button emits.

It points at the action line, the line after the misplaced display. The button turned the model into an event, the heading showed that event's row and passed it on — a display releases what it is fed — and the action is the first line that wants the event back: atCase @"Order" expects a variant and is handed the record the display released. So read the two sides in the message, Variant against Record, and look upstream for the stage that changed the shape: an emitter standing above a display that reads the model. Put the heading back above the button, where it is on the screen. The skill's writing.md lists the other common messages under When it does not compile.

6 · Compile-green is not done — run it

The types prove the wiring, not that data reaches the screen: a record merge withholds until every field of its row has been fed, so the session ends by running the app. A pane that stays blank is a knowledge gate withholding — a named failure, not a mystery: the 3-second starvation watchdog prints the gate and its missing fields to the console, and the emission trace logs every propagation decision (see the tracing note).
