How a bambik app is written

Every demo page on this site shows a finished listing. This page shows what a listing hides: the session that produces one — the order the code is written in, and what the compiler says back after each step. The session below is real: the app is a small pizza-order form — a text field, a live line, an Order button, a confirmation snackbar — in the two-module layout every bambik app ships with (a view module and a logic module beside it), and every compiler response is verbatim output of bambik's pinned PureScript compiler (0.15.16-variant.7, the variant fork — whose hole reporting through constraint failures this very workflow motivated), captured by replaying the session. The screenshots at the end are the session's own app, running.

The method rests on one rule, the anchor invariant (see the code style note): every view line names exactly one semantic anchor — the model field it edits (@l on an editor or selector), the business case it emits or shows (@l on an emitter, pane or status), the named read function it renders, or nothing at all, chrome writing nothing. So the view is written first, with typed holes (?orderLine — a name the compiler must type rather than resolve) standing in for the functions that do not exist yet, and the logic module is written second, to the names and types the view demanded.

1 · The view, whole, before any logic exists

You know what the screen is before you know what the model is: a field for the pizza, a line showing what's in the oven, a button that orders, a toast that confirms. Write exactly that. Three term obligations enter as holes — the display's read, the confirmation copy, the seed. Note what is not a hole: the field anchor (@"Pizza"), the case anchor (@"Order", stated once on the button and adopted once by the snackbar), and the chrome (elevation5, card, headlineSmall) are complete as written.

src/Order.purs

module Order (orderApp) where

import Prelude ((#), ($), Unit)

import Effect (Effect)
import PUI (forCase, with)
import PUI.Web.HTML (body, shown, text)
import PUI.Web.MDC3 (button, card, elevation5, filledTextField, headlineSmall, snackbar)
import QualifiedDo.Category as Category

orderApp :: Effect Unit
orderApp =
  body $
    elevation5 $
      card $ ( Category.do
          filledTextField @"Pizza" {}
          headlineSmall (text ?orderLine) # shown
          button @"Order" {}
          snackbar # forCase @"Order" ?confirmedLine
      ) # with ?start

The refusal is the design, not an obstacle. shown reads a sub-row of the model (Union read extra row: what the line reads, plus everything it doesn't, is the model) — and which sub-row a display reads is a business decision, so the compiler declines to make it. But the fed row it prints already carries ( "Pizza" :: String | t4 ): the editor's field anchor taught the pipeline the model's first field before any logic exists. The display hole reports the same contract from its side — a read Record t0 -> String over a sub-row of that row. The two holes further down are still shapeless: constraint solving stops at the first refusal, so each decision you land sharpens the next report. The first decision: this line shows the pizza. Write the read function down, its footprint stated as a closed row.

2 · One decision in — every refusal gone

src/OrderLogic.purs — the logic module begins

module OrderLogic (orderLine) where

import Prelude ((<>))

orderLine :: { "Pizza" :: String } -> String
orderLine r = "In the oven: " <> r."Pizza"

This is the other side of the workflow. The confirmation copy sits at a pinned position — the button replays the row it is fed, so the payload of case "Order" is exactly the pipeline's row, and the hole comes back complete, suggestions included: _."Pizza" would do, and the compiler even offers OrderLogic.orderLine, the function written thirty seconds earlier. At pinned positions the compiler speaks first; at subsuming positions (the display read above) the footprint is yours to state — the signature is the decision.

The view computed the model — and with both read functions stating closed footprints, the row is now closed: the app's state is exactly { "Pizza" :: String }, derived from what the lines demanded, declared nowhere. The seed is that row's value at t=0, business data under a business name — never initial.

4 · Green

module OrderLogic (confirmedLine, orderLine, plainMargherita) where

Every anchor resolved: orderLine and confirmedLine are pure functions under unit test in the logic module, @"Pizza" is both the field's caption and its name in the model, @"Order" is both the button's caption and the case the snackbar adopts, and the chrome names nothing because it writes nothing.

5 · Compile-green is not done — run it

The types prove the wiring, not that data reaches the screen: a record merge withholds until every field of its row has been fed, so the session ends by running the app. A pane that stays blank is a knowledge gate withholding — a named failure, not a mystery: the 3-second starvation watchdog prints the gate and its missing fields to the console, and the emission trace logs every propagation decision (see the tracing note).
